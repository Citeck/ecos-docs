.. _sizing_external:

Требования к внешним сервисам
==============================

Страница описывает требования к PostgreSQL, S3-совместимому хранилищу и OpenSearch, когда эти компоненты выносятся за пределы кластера Kubernetes или за пределы ВМ с контейнерами платформы. Требования сформулированы **без привязки к конкретному провайдеру** и подходят как для managed-сервисов, так и для развёртывания на отдельных виртуальных машинах.

Ресурсы приведены с запасом и уточняются по фактическому объёму документооборота — см. :ref:`правила пересчёта <sizing_recalc>`.

**Обоснование ресурсов.** Минимум — **2 vCPU / 4 GiB** по :ref:`k8s-resource-management`, валидирован нагрузочным тестированием (:ref:`load_testing`). Норматив на 2000 именных пользователей — 8 vCPU / 16 GiB; RAM взята с двукратным запасом. Диск: объём БД ≈ 0.6 × объёма контента (500 ГБ) + ~30 % на WAL, временные файлы и служебные данные. Ресурсы в зависимости от объёма БД — см. :ref:`sizing_recalc`.

.. note::

    При размещении PostgreSQL **на общей ВМ** вместе с контейнерами платформы ресурсы снижаются до 4 vCPU / 16 GiB на целевом профиле (вместо 8 vCPU / 32 GiB): ядра и файловый кэш делятся со всей платформой, а ``shared_buffers`` при 16 GiB составляет ~4 GiB, чего достаточно для базы до ~500 ГБ. См. :ref:`sizing_docker`.

    При размещении **внутри кластера Kubernetes** значения пода 2 vCPU / 4 GiB покрывают тестовый и приёмочный сценарии; для продуктива применяются значения из таблицы выше. См. :ref:`sizing_k8s`.

**Отказоустойчивость.** Реплика PostgreSQL в расчёте **не закладывается** (1 хост). При необходимости отказоустойчивости СУБД добавляется реплика (2-й хост) и/или переход на managed-сервис с HA; ресурсы на кластеризацию — репликация, Patroni, etcd, балансировщик подключений — определяются отдельно. Обязательны регулярные автоматические резервные копии (``pg_basebackup`` + архив WAL).

**Если на отдельной ВМ:** развернуть S3-совместимое хранилище на одном узле, например SeaweedFS. Test — 1 ВМ **2 vCPU / 4 GiB / 150 ГБ SSD**. Prod — 1 ВМ **2 vCPU / 4 GiB / от 500 ГБ SSD** + регулярное резервное копирование.

OpenSearch
-----------

OpenSearch обеспечивает полнотекстовый поиск и индексацию контента и атрибутов (см. :ref:`Архитектура <architecture>`). Компонент включается по необходимости: конфигурации «без полнотекстового поиска» в расчётах приведены отдельно.

.. list-table::
   :header-rows: 1
   :widths: 22 39 39
   :class: tight-table

   * - Параметр
     - Test
     - Production
   * - Узлы
     - 1
     - **1**
   * - vCPU
     - 4
     - **8**
   * - RAM
     - 16 GiB
     - **32 GiB**
   * - Heap JVM
     - 8 GiB
     - **16 GiB**
   * - Диск
     - 100 ГБ NVMe
     - **300 ГБ NVMe** (индексы ~250 ГБ при 500 ГБ контента)

**Ориентир по ресурсам:** ~1 GiB heap на 20–30 ГБ индексов; heap не более 31 GiB и не более 50 % RAM узла. Объём индексов ≈ 0.5 × объёма контента.

**Размещение.** Рекомендуется вынос за пределы кластера — managed-сервис или выделенные ВМ. Для тестовых контуров при небольших объёмах индексов допустимо размещение внутри кластера Kubernetes; в этом случае требуются:

* отдельный node pool с локальными NVMe;
* Guaranteed QoS (``requests = limits``);
* настройки уровня хоста: ``vm.max_map_count = 262144``, отключённый swap.

При размещении **на общей ВМ** вместе с контейнерами платформы применяется сокращённая конфигурация: на продуктиве — 4 vCPU / 16 GiB (при 250 ГБ индексов heap 8 GiB находится у нижней границы правила: поиск работает, но холодные запросы выполняются медленнее), на тестовом контуре — 2 vCPU / 4 GiB при индексах до 50 ГБ. При росте индексов свыше ~500 ГБ применяется 8 vCPU / 32 GiB либо вынос поиска на отдельную ВМ. См. :ref:`sizing_docker`.

**Кластеризация OpenSearch** в расчёте не учтена — заложен один узел. При необходимости отказоустойчивого поиска (кворум из трёх узлов с репликами индексов) ресурсы умножаются на три: **24 vCPU / 96 GiB / 900 ГБ NVMe**; объём индексов при этом также возрастает кратно числу узлов с репликами.
