.. _sizing_k8s:

Сайзинг в Kubernetes
=====================

Страница описывает расчёт **worker-нод** Kubernetes-кластера для развёртывания Citeck с числом именных пользователей **до 2000**. Общие допущения, целевая нагрузка, состав контейнеров и правила пересчёта — на странице :ref:`Типовой сайзинг <sizing>`.

.. note::

    * Учитываются только **worker-ноды**; управляющие компоненты кластера (control plane / master-ноды) в расчёт не входят.
    * Ресурсы подов взяты из раздела :ref:`Менеджмент ресурсов подов и контейнеров <k8s-resource-management>`; сводная таблица — :ref:`Состав и ресурсы контейнеров платформы <sizing_containers>`.
    * Развёртывание в Kubernetes выполняется с помощью Helm chart (только в Enterprise-поставке) — см. :ref:`Параметры конфигурации Helm chart <helm-chart-config>`.

Типоразмер worker-ноды
-----------------------

За единицу расчёта принята worker-нода **16 vCPU / 32 GiB**.

.. list-table::
   :header-rows: 1
   :widths: 40 60
   :class: tight-table

   * - Показатель
     - Значение
   * - Типоразмер worker-ноды
     - 16 vCPU / 32 GiB
   * - Доступно для подов платформы
     - ~14 vCPU / ~27 GiB
   * - Накладные расходы ноды
     - ~15–20 % — ``kube-reserved`` и ``system-reserved``, агенты мониторинга и сбора логов (DaemonSet)

Масштабирование сверх целевого профиля — **горизонтальное**: добавление worker-нод того же типоразмера, тиражирование и кластеризация микросервисов в соответствии с нагрузкой.

Рекомендации по размещению общесистемных компонентов
------------------------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 18 34 48
   :class: tight-table

   * - Компонент
     - Рекомендация
     - Комментарий
   * - **PostgreSQL**
     - Вынести за пределы кластера — managed-сервис или выделенные ВМ
     - Ресурсы на кластеризацию (репликация, Patroni, etcd, балансировщик) в настоящем расчёте **не учитываются** и определяются отдельно. :ref:`Требования к PostgreSQL <sizing_pg>`
   * - **S3-хранилище**
     - Предпочтительно managed Object Storage; в базовом расчёте заложено self-hosted S3-хранилище внутри кластера — **1 узел**
     - Кластеризация хранилища подлежит отдельному обсуждению. :ref:`Требования к S3-хранилищу <sizing_s3>`, :ref:`настройка в интерфейсе <s3_storage>`
   * - **RabbitMQ**
     - Опционально: вынести при наличии managed-сервиса
     - Нагрузочное тестирование проводилось с RabbitMQ внутри кластера, поэтому в базовом расчёте он оставлен на worker-нодах
   * - **OpenSearch**
     - Вынести за пределы кластера — managed-сервис или выделенные ВМ
     - Для тестовых контуров при небольших объёмах индексов допустимо размещение внутри кластера. При таком размещении требуются отдельный node pool с локальными NVMe-дисками, Guaranteed QoS (``requests = limits``) и настройки на уровне хоста (``vm.max_map_count = 262144``, отключённый swap). :ref:`Требования к OpenSearch <sizing_opensearch>`

Вне расчёта worker-нод также остаются серверные компоненты мониторинга и сбора логов (их агенты на нодах учтены в накладных расходах), инструменты CI/CD и резервное копирование.

Продуктивный кластер
---------------------

Потребность продуктивного кластера: Σ requests **9.60 vCPU / 22.71 GiB**, Σ limits **23.00 vCPU / 24.96 GiB**.

.. list-table::
   :header-rows: 1
   :widths: 24 20 15 15 26
   :class: tight-table

   * - Вариант
     - Ноды
     - Всего ресурсов
     - Доступно для подов
     - Комментарий
   * - **Рекомендуемый (N+1)**
     - **2 × (16 vCPU / 32 GiB)**
     - 32 vCPU / 64 GiB
     - ~28 vCPU / ~54 GiB
     - Контур целиком помещается на одну ноду (limits 24.96 ≤ 27 GiB), поэтому при отказе любой из двух нод оставшаяся вмещает всю нагрузку
   * - С запасом на рост и распределение реплик
     - 3 × (16 vCPU / 32 GiB)
     - 48 vCPU / 96 GiB
     - ~42 vCPU / ~81 GiB
     - Разнесение реплик критичных сервисов по нодам (anti-affinity), обновления без деградации, запас на рост нагрузки сверх 2000 именных пользователей

Приложение. Размещение PostgreSQL и OpenSearch внутри кластера
----------------------------------------------------------------

Оба компонента рекомендуется выносить за пределы кластера (см. рекомендации по размещению выше), поэтому в базовый расчёт они не входят. При их размещении внутри кластера к суммам :ref:`базовой таблицы контейнеров <sizing_containers>` добавляется:

.. list-table::
   :header-rows: 1
   :widths: 32 17 17 17 17
   :class: tight-table

   * - Компонент
     - Requests CPU
     - Requests MEM
     - Limits CPU
     - Limits MEM
   * - PostgreSQL (в кластере)
     - 2
     - 4 Gi
     - 2
     - 4 Gi
   * - OpenSearch (в кластере, 1 узел)
     - 4
     - 16 Gi
     - 4
     - 16 Gi
   * - **Итого с PostgreSQL**
     - **11.60 vCPU**
     - **26.71 Gi**
     - **25.00 vCPU**
     - **28.96 Gi**
   * - **Итого с PostgreSQL и OpenSearch**
     - **15.60 vCPU**
     - **42.71 Gi**
     - **29.00 vCPU**
     - **44.96 Gi**

.. warning::

    PostgreSQL и OpenSearch указаны в тестовой конфигурации: внутри кластера OpenSearch допустим только для тестовых контуров, а PostgreSQL в размере 2 vCPU / 4 GiB достаточен для тестового и приёмочного сценариев. Для продуктивной эксплуатации на 2000 именных пользователей ресурсы СУБД определяются по разделу :ref:`sizing_pg` (8 vCPU / 32 GiB).

    Уже при размещении в кластере одного PostgreSQL потребность по limits памяти (28.96 GiB) превышает объём, доступный для подов на одной ноде (~27 GiB): резерв N+1 на двух нодах не обеспечивается. Количество worker-нод в этом случае, как и при размещении обоих компонентов, пересчитывается отдельно.
