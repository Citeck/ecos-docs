.. _sizing_docker:

Сайзинг на одной ВМ: Citeck Launcher
=====================================

Страница описывает расчёт ресурсов ВМ для развёртывания, при котором все компоненты платформы запускаются в контейнерах **на одной ВМ**. Оркестрация уровня кластера (Kubernetes, Swarm) не используется. Общие допущения, целевая нагрузка, состав контейнеров и правила пересчёта — на странице :ref:`Типовой сайзинг <sizing>`.

.. important::

    **Единственный рекомендуемый способ развёртывания на одной ВМ — Citeck Launcher 2.x в** :ref:`серверном режиме <launcher_server>`. Лончер устанавливает и обновляет платформу, управляет её жизненным циклом через CLI и systemd, настраивает TLS, ведёт снэпшоты данных и выполняет диагностику. Установка — :ref:`server_quick_start`, команды — :ref:`server_commands`.

    Docker Compose как способ развёртывания вне Kubernetes **больше не поддерживается**: конфигурации Docker Compose для новых версий Citeck выпускаться не будут. Перенос существующей установки с Docker Compose под управление лончера — :ref:`migration_from_compose`.

    :depth: 2

Контуры
--------

Одна ВМ на каждую среду:

* **Test** — разработка, отладка, приёмочное тестирование;
* **Prod** — продуктив.

При схеме с тремя средами (**Dev + Test + Prod**) добавляется ещё одна ВМ по конфигурации тестового контура.

Типовые конфигурации
---------------------

.. list-table::
   :header-rows: 1
   :widths: 40 30 30
   :class: tight-table

   * - Профиль
     - Без полнотекстового поиска
     - С полнотекстовым поиском (OpenSearch)
   * - 100 именных — минимальная конфигурация
     - 8 CPU / 24 ГБ RAM / 240 ГБ SSD
     - 8 CPU / 32 ГБ RAM / 300 ГБ SSD
   * - 100 именных — рекомендуемая конфигурация
     - 16 CPU / 32 ГБ RAM / 500 ГБ SSD
     - 16 CPU / 40 ГБ RAM / 500 ГБ SSD
   * - до 2000 именных (500 одновременных)
     - 16 CPU / 48 ГБ RAM / от 1.3 ТБ SSD
     - 24 CPU / 64 ГБ RAM / от 1.3 ТБ SSD

Объём дискового пространства зависит от планируемого объёма хранимых документов — см. «Дисковая подсистема» в соответствующей вкладке ниже.

.. note::

    Требуемый объём памяти мало зависит от числа пользователей: :ref:`состав контейнеров <sizing_containers>` одинаков и для 100, и для 2000 именных пользователей. Разница между профилями складывается из ресурсов PostgreSQL (4 GiB на малой базе против 16 GiB на целевом профиле) и запаса на пики. С процессором иначе: контейнеры делят ядра ВМ между собой, и при нехватке CPU сервисы замедляются, а не завершаются, как при нехватке памяти. Поэтому младшим профилям достаточно меньшего числа CPU.

    Значения в :ref:`таблице контейнеров <sizing_containers>` приведены по ``limits`` — это потолок, а не фактическое потребление: на малых установках контейнеры расходуют заметно меньше памяти, что и позволяет уместить профиль на 100 пользователей в 24–32 ГБ.

Расчёт ресурсов ВМ по профилям
-------------------------------

.. tab-set::

    .. tab-item:: До 100 именных пользователей

        Профиль для небольших внедрений, демонстрационных и тестовых контуров.

        **Минимальная конфигурация — 8 CPU / 24 ГБ RAM.** Предполагает:

        * отключение неиспользуемых модулей (Ecos Ecom, Service Desk, EDI, Transformations — по 1 GiB каждый). В :ref:`серверном режиме лончера <launcher_server>` приложения отключаются командой ``citeck stop`` — см. :ref:`server_commands`;
        * уменьшенные лимиты контейнеров: у Java-сервисов с ``-Xmx256m`` фактическое потребление 400–600 МиБ вместо 1 GiB;
        * PostgreSQL в минимальной конфигурации (2 vCPU / 4 GiB).

        **Рекомендуемая конфигурация — 16 CPU / 32 ГБ RAM** — полный набор приложений без отключений и запас на пики.

        .. warning::

            16 ГБ ОЗУ, указанные в системных требованиях :ref:`Citeck Launcher <citeck_launcher>`, — это минимум для **запуска** Community-поставки без нагрузки, а не для продуктивной эксплуатации. Enterprise-поставка с полным набором приложений уже в простое занимает около 16 ГБ и в этот объём не помещается. Для рабочей установки с полным набором приложений необходимо **24–32 ГБ**.

             - 100 ГБ

        Целевой профиль расчёта: до 2000 именных, до 500 одновременных пользователей, базовый объём контента 500 ГБ.

        Потребность собрана снизу вверх — по :ref:`ресурсам контейнеров <sizing_containers>`, с добавлением СУБД, поискового движка и накладных расходов ВМ.

        .. list-table::
           :header-rows: 1
           :widths: 60 20 20
           :class: tight-table

           * - Группа компонентов
             - vCPU
             - RAM
           * - Контейнеры платформы (микросервисы, Keycloak, Zookeeper, RabbitMQ, Onlyoffice, S3-хранилище)
             - 9.6 (по ``requests``)
             - 25 GiB (по ``limits``)
           * - PostgreSQL — на общей ВМ с остальными контейнерами
             - 4
             - 16 GiB
           * - OpenSearch — при включении полнотекстового поиска, на общей ВМ
             - 4
             - 16 GiB
           * - ОС, Docker daemon, агенты мониторинга и сбора логов
             - 2
             - 4 GiB

        Ресурсы PostgreSQL снижены относительно расчёта для выделенного сервера (8 vCPU / 32 GiB): на общей ВМ ядра и файловый кэш делятся со всей платформой, а ``shared_buffers`` при 16 GiB составляет ~4 GiB, чего достаточно для базы до ~500 ГБ. При выносе СУБД на отдельную ВМ или в managed-сервис применяются полные 8 vCPU / 32 GiB — см. :ref:`sizing_pg`.

        OpenSearch на общей ВМ также взят в сокращённой конфигурации: при 250 ГБ индексов heap 8 GiB (половина от 16 GiB RAM) находится у нижней границы правила «1 GiB heap на 20–30 ГБ индексов» — поиск работает, но объём файлового кэша ограничен и холодные запросы выполняются медленнее. При росте индексов свыше ~500 ГБ применяется конфигурация 8 vCPU / 32 GiB либо вынос поиска на отдельную ВМ — см. :ref:`sizing_opensearch`.

Ограничения схемы с одной ВМ
------------------------------

* **Отказоустойчивость отсутствует** — ВМ является единой точкой отказа.
* **Обновления выполняются с остановкой сервисов**, rolling update недоступен.
* **Масштабирование — вертикальное**, увеличением ресурсов ВМ. Тиражирование отдельных микросервисов (кластеризация) в :ref:`Citeck Launcher <launcher_server>` пока не поддерживается. Оно появится в будущих версиях, но только в пределах одной ВМ: многосерверные конфигурации лончер не обслуживает.
* **Кластеризация PostgreSQL, S3 и OpenSearch** в рамках одной ВМ не предусмотрена и требует выноса этих компонентов на отдельные ВМ — см. :ref:`sizing_external`.
* **Компоненты искусственного интеллекта**, резервное копирование и инструменты мониторинга в расчёт не входят — см. «Что не входит в расчёт» на странице :ref:`sizing`.

.. tip::

    При наличии требований по RPO / RTO либо при численности свыше 2000 именных пользователей рекомендуется переход на :ref:`развёртывание в Kubernetes <sizing_k8s>`. Тиражирование ключевых микросервисов (Ecos Model, Gateway, Process) в пределах одной ВМ появится в будущих версиях Citeck Launcher. Ориентир для такой конфигурации — **24–32 CPU / 64–96 ГБ**; отказоустойчивости она не даёт — ВМ остаётся единой точкой отказа.
