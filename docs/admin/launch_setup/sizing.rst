Сайзинг: тестовая и продуктивная среда
=========================================

Страница содержит рекомендации по планированию инфраструктуры для развёртывания Citeck с числом именных пользователей **до 1 000**.

.. note::

    * Учитываются только **Worker Node** Kubernetes-кластера (control plane / master не учитывается).
    * Данные по ресурсам подов — из официальной документации Citeck: :ref:`k8s-resource-management`.
    * Конфигурация подтверждена нагрузочным тестированием: **1 000 одновременных пользователей** в течение 1 часа (~2 млн запросов, средний отклик 6.88 мс, 99-й перцентиль 47 мс).

Готовятся **две среды**, каждая в **двух вариантах**:

* **Вариант A (всё в K8s):** PostgreSQL и S3-совместимое хранилище (self-hosted, например MinIO) работают внутри кластера.
* **Вариант B (PG + S3 вынесены):** PostgreSQL и S3 — внешние сервисы (требования к ним — раздел :ref:`Требования к внешним сервисам<sizing-external-services-b>`).

.. contents::

Методика и допущения
---------------------

* **Requests** — гарантированный минимум, на нём строится планирование суммарной ёмкости нод. **Limits** — верхняя граница потребления (для оценки пиков).
* К сумме requests добавляется overhead на системные компоненты ноды (kubelet, CNI, DaemonSet'ы мониторинга/логирования, kube-proxy) — **~20%**.
* Память по limits ≈ requests: burst-запаса по RAM почти нет, нода должна гарантированно вмещать сумму requests.
* Управляющие компоненты кластера не учитываются.
* **1 000 именных пользователей ≠ 1 000 одновременных.** Реальная одновременность для небольшого внедрения — обычно 10–20% от именных (~100–200 сессий). Поэтому **ресурсы подов между Test и Prod не меняются** — продуктивная среда отличается только **резервированием** (N+1 worker-ноды), а не более «тяжёлыми» подами.
* Уровень отказоустойчивости Prod: **N+1 по worker-нодам**. PostgreSQL — **1 хост (без реплики)**. Реплика PostgreSQL, кластеризация RabbitMQ / Zookeeper и мульти-зональность — опциональны (см. раздел :ref:`Примечания<sizing-notes>`), при необходимости закладываются дополнительно.

Тестовая среда
---------------

.. note::

    Предполагается, что тестовая среда **не является полной копией продуктивной** (меньший объём данных и документов). Если тест используется как копия прода (нагрузочное / приёмочное тестирование на реальном объёме данных) — **дисковые ресурсы нужно нарастить до продуктивных значений** (PostgreSQL PVC, S3 / MinIO, PVC сервисов). Ресурсы CPU / RAM при этом остаются прежними.

    **Резерва на отказ ноды в тестовой среде не закладывается.** Если резерв нужен (переживание отказа узла / drain при обновлении без простоя) — добавляется 3-я нода той же конфигурации (режим N+1, как в проде).

Примечания
-----------

* Сайзинг рассчитан по **requests** (минимум для стабильной работы) — корректно для планирования ёмкости нод. Сумма **limits** показана для оценки пиков.
* Память по limits ≈ requests — нода должна гарантированно вмещать сумму requests; для прода RAM нод берётся с запасом, чтобы пережить отказ ноды (N+1).
* Ресурсы PostgreSQL заданы от минимума Read The Docs (2 vCPU / 2 Gi): **×2 для теста (4/4)** и **×3 для прода (6/6)**; **реплика PostgreSQL не закладывается** (1 хост).
* **OpenSearch** (полнотекстовый поиск/индексация метаданных) в расчёт не включён. При необходимости — развёртывается отдельно (managed либо отдельный пул нод/ВМ) и закладывается дополнительно.
* Для **повышенного HA** дополнительно (опционально): реплика PostgreSQL (2-й хост), worker-ноды по 3 зонам, кластер RabbitMQ (3 узла) и ансамбль Zookeeper (3 узла). В текущем расчёте заложен уровень **N+1 по worker-нодам** без реплики PostgreSQL.
* Объёмы дисков заложены с запасом; уточняются под реальный объём документов и историю.
