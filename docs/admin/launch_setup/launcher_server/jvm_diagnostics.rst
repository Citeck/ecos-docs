Диагностика JVM и выгрузка файлов
==================================

Начиная с версии **2.10** лаунчер умеет снимать дампы потоков и памяти Java-приложений платформы и забирать с сервера файлы, которые создают контейнеры. JDK в образе для этого не нужен: лаунчер подключается к JVM сам.

.. contents::
    :local:
    :depth: 2

Каталог выгрузки
-----------------

У каждого контейнера есть каталог для артефактов, которые он создаёт (дампы памяти, дампы БД, отчёты):

- внутри контейнера -- ``/citeck/export`` (путь также передаётся в переменной окружения ``CITECK_EXPORT_DIR``);
- на хосте -- ``/opt/citeck/data/runtime/<namespace>/export/<app>/``.

Файлы из этого каталога просматриваются, скачиваются и удаляются командой ``citeck export``.

Дамп потоков: citeck jstack
----------------------------

.. code-block:: bash

    citeck jstack <app> [flags]

.. list-table::
    :widths: 30 70
    :header-rows: 1
    :class: tight-table

    * - Флаг
      - Описание
    * - ``-l``, ``--locks``
      - Включить информацию о блокировках ``java.util.concurrent``

Дамп выводится в stdout:

.. code-block:: bash

    citeck jstack emodel > emodel-threads.txt

Дамп памяти: citeck jmap
-------------------------

.. code-block:: bash

    citeck jmap <app> [flags]

.. list-table::
    :widths: 30 70
    :header-rows: 1
    :class: tight-table

    * - Флаг
      - Описание
    * - ``-o``, ``--output <path>``
      - Куда сохранить дамп (по умолчанию -- под собственным именем в текущем каталоге)
    * - ``--keep``
      - Оставить дамп в каталоге выгрузки приложения, не скачивая его
    * - ``--histo``
      - Вывести гистограмму классов вместо дампа (ничего не записывается)

Дамп записывается в каталог выгрузки приложения (сжатым -- для Java 17 и новее), затем скачивается в текущий каталог и удаляется с сервера. На время снятия дампа проверка живости приложения приостанавливается, чтобы долгая пауза JVM не привела к перезапуску контейнера.

.. code-block:: bash

    # Снять дамп и сохранить в /tmp
    citeck jmap emodel -o /tmp/emodel.hprof.gz

    # Гистограмма классов
    citeck jmap emodel --histo | head -40

.. warning::

    Дамп памяти содержит в открытом виде пароли, токены и персональные данные, которые были в памяти процесса. Файл сохраняется с правами ``0600`` -- не ослабляйте их и удаляйте дамп после анализа.

Произвольные команды: citeck jcmd
----------------------------------

.. code-block:: bash

    citeck jcmd <app> <command> [args...]

Выполняет любую диагностическую команду, которую поддерживает JVM приложения. Список команд выводит сама JVM:

.. code-block:: bash

    citeck jcmd eapps help
    citeck jcmd eapps VM.flags
    citeck jcmd eapps GC.heap_info

.. note::

    Команды ``jstack``, ``jmap`` и ``jcmd`` работают, пока контейнер приложения существует -- в том числе в статусе ``STARTING`` и у зависшего или падающего приложения, когда диагностика нужнее всего. Для остановленного приложения и для приложений, не являющихся JVM (например, ``postgres`` или ``proxy``), команда вернёт понятную ошибку.

Файлы выгрузки: citeck export
------------------------------

.. code-block:: bash

    citeck export ls <app>            # список файлов, новые сверху
    citeck export get <app> <file>    # скачать файл
    citeck export rm <app> <file>     # удалить файл

**Флаги** ``export get`` **:**

.. list-table::
    :widths: 30 70
    :header-rows: 1
    :class: tight-table

    * - Флаг
      - Описание
    * - ``-o``, ``--output <path>``
      - Куда сохранить файл (по умолчанию -- под собственным именем в текущем каталоге)
    * - ``--force``
      - Перезаписать существующий файл назначения
    * - ``--rm``
      - Удалить файл из каталога выгрузки после успешного скачивания

**Пример:**

.. code-block:: bash

    # Найти дамп, сохранённый при OutOfMemoryError
    citeck export ls emodel

    # Скачать его и удалить с сервера
    citeck export get emodel <file> -o /tmp/<file> --rm

Автоматическая диагностика
---------------------------

Лаунчер собирает часть диагностики без участия администратора:

- **Дамп памяти при OutOfMemoryError.** Java-приложения платформы запускаются с сохранением дампа памяти при ``OutOfMemoryError`` в каталог выгрузки (сжатым, если JVM это поддерживает). Хранится только **самый свежий** дамп, поэтому цикл падений не заполнит диск. Если в ``JAVA_OPTS`` приложения уже заданы собственные параметры сохранения дампа, лаунчер их не меняет.

  .. note::

      Дамп создаётся только при ошибке ``OutOfMemoryError`` внутри JVM. Если контейнер превысил лимит памяти и был завершён ядром (OOM Killer), JVM не успевает ничего записать.

- **Дамп потоков перед перезапуском.** Если приложение не проходит проверку живости и реконсилер перезапускает контейнер, перед этим снимаются дамп потоков и хвост лога. Файл сохраняется в ``/opt/citeck/data/runtime/<namespace>/diagnostics/<app>/`` и хранится 7 дней.

Память JVM
-----------

Все пулы памяти JVM (heap, direct-память, metaspace, code cache) рассчитываются от лимита памяти контейнера (``memoryLimit``). Заданный вручную ``heapSize`` задаёт **максимальный** размер heap и сохраняется как есть, остальные пулы рассчитываются вокруг него. Heap не резервируется целиком при старте: приложение занимает память по мере надобности.

Благодаря этому утечка в любом пуле приводит к ``OutOfMemoryError`` (и дампу памяти), а не к завершению контейнера ядром без диагностики.

Для Alfresco и Solr (Java 8) память также рассчитывается от лимита контейнера: по умолчанию лимит Alfresco -- 8 ГБ, Solr -- 2560 МБ.
