Архитектура
============

Citeck Launcher -- единый бинарный файл на Go (~27 МБ) без внешних зависимостей (pure Go, без CGO). Он совмещает в себе CLI-клиент и фоновый демон, взаимодействующий с Docker Engine для управления контейнерами платформы.

.. contents::
    :local:
    :depth: 2

Общая схема
-------------

.. code-block:: text

    +------------------+       Unix socket       +------------------+
    |                  | ----------------------> |                  |
    |   CLI (citeck)   |       HTTP API          |   Daemon         |
    |                  | <---------------------- |   (HTTP server)  |
    +------------------+                         +--------+---------+
                                                          |
                                                   Docker SDK
                                                          |
                                                 +--------v---------+
                                                 |                  |
                                                 |   Docker Engine  |
                                                 |                  |
                                                 +--------+---------+
                                                          |
                                  +------------------------------------------+
                                  |                  |                       |
                           +------v------+    +------v------+    +----------v--+
                           |  postgres   |    |  keycloak   |    |    eapps    |
                           +-------------+    +-------------+    +-------------+
                           |  zookeeper  |    |  rabbitmq   |    |    emodel   |
                           +-------------+    +-------------+    +-------------+
                           |   proxy     |    |   pgadmin   |    |    uiserv   |
                           +-------------+    +-------------+    +-------------+

**Компоненты:**

- **CLI** -- команды ``citeck``, форматирование вывода (текст/JSON), интерактивные TUI-промпты
- **Daemon** -- HTTP-сервер на Unix-сокете, обслуживающий REST API и SSE-поток событий. В серверном режиме демон не открывает сетевых портов и не предоставляет веб-интерфейс -- управление только через CLI
- **Docker SDK** -- прямое взаимодействие с Docker Engine через официальный Go SDK
- **Контейнеры** -- Docker-контейнеры с компонентами платформы Citeck

Взаимодействие CLI и демона
----------------------------

CLI и демон общаются через **Unix-сокет** (``/run/citeck/daemon.sock``). Все команды CLI отправляют HTTP-запросы к демону:

.. code-block:: text

    citeck status  ->  GET  /api/v1/namespace
    citeck start   ->  POST /api/v1/namespace/start
    citeck stop    ->  POST /api/v1/namespace/stop
    citeck reload  ->  POST /api/v1/namespace/reload
    citeck logs    ->  GET  /api/v1/apps/{name}/logs
    citeck deps    ->  GET  /api/v1/namespace/dependencies

Для мониторинга в реальном времени (``citeck status --watch``, ``citeck start``) используется **SSE** (Server-Sent Events), а не WebSocket.

Жизненный цикл контейнеров
----------------------------

Каждое приложение проходит через состояния:

.. code-block:: text

    READY_TO_PULL --> PULLING --> READY_TO_START --> DEPS_WAITING --> STARTING --> RUNNING
         ^              |                                                |
         |              v                                                v
         |         PULL_FAILED                                      START_FAILED
         |                                                               |
         +---------------------------------------------------------------+
                   (reconciler retry: 1m -> 10m)

**Описание состояний:**

.. list-table::
    :widths: 25 75
    :header-rows: 1

    * - Состояние
      - Описание
    * - ``READY_TO_PULL``
      - Начальное состояние, готово к загрузке образа
    * - ``PULLING``
      - Загрузка Docker-образа
    * - ``PULL_FAILED``
      - Ошибка загрузки образа. При ошибке авторизации в реестре автоповтор приостанавливается до ввода учётных данных
    * - ``READY_TO_START``
      - Образ получен, контейнер готов к созданию
    * - ``DEPS_WAITING``
      - Ожидание запуска зависимостей (например, postgres перед keycloak). В ``citeck status`` рядом со статусом указано, чего именно ждёт приложение: ``DEPS_WAITING ← postgres``
    * - ``STARTING``
      - Контейнер создан и запускается
    * - ``RUNNING``
      - Контейнер работает, проверка готовности пройдена
    * - ``START_FAILED``
      - Контейнер не смог запуститься
    * - ``UPDATING``
      - Контейнер пересоздаётся из-за изменения конфигурации или образа
    * - ``STOPPING``
      - Контейнер останавливается
    * - ``STOPPING_FAILED``
      - Остановка не завершилась вовремя; реконсилер повторит её
    * - ``STOPPED``
      - Контейнер остановлен

При сбое запуска реконсилер автоматически повторяет попытку с экспоненциальным backoff: 1 минута, 2 минуты, 4 минуты, ..., до максимума 10 минут.

Статусы namespace
~~~~~~~~~~~~~~~~~~

.. list-table::
    :widths: 25 75
    :header-rows: 1

    * - Статус
      - Описание
    * - ``STARTING``
      - Приложения запускаются
    * - ``RUNNING``
      - Все приложения, которые должны работать, запущены -- namespace целиком готов к работе
    * - ``STALLED``
      - Запуск не может завершиться сам: например, приложение ждёт зависимость, остановленную вручную. В этом состоянии ``citeck health`` сообщает «нездоров», а ``citeck deps upgrade`` отказывает. Запустите остановленную зависимость (``citeck start <app>``) -- namespace вернётся в ``RUNNING`` сам
    * - ``STOPPING``
      - Приложения останавливаются
    * - ``STOPPED``
      - Namespace остановлен

Порядок запуска
----------------

Приложения запускаются с учётом зависимостей:

.. code-block:: text

    Фаза 1:  postgres
    Фаза 2:  keycloak, zookeeper, rabbitmq
    Фаза 3:  Веб-приложения (eapps, emodel, gateway, ...)
    Фаза 4:  proxy

Каждое приложение ожидает готовности своих зависимостей (состояние ``DEPS_WAITING``), прежде чем начать запуск. Зависимость, остановленная вручную (``citeck stop <app>``), сама не стартует: зависящее от неё приложение остаётся в ``DEPS_WAITING``, а namespace переходит в ``STALLED``, пока зависимость не будет запущена. Явный запуск приложения (``citeck start <app>``) не поднимает его остановленные зависимости -- их нужно запустить отдельно.

Циклическая зависимость между приложениями останавливает генерацию конфигурации с ошибкой; ссылка в ``dependsOn`` на несуществующее приложение в ``namespace.yml`` также является ошибкой.

Порядок остановки -- обратный:

.. code-block:: text

    Фаза 1:  proxy
    Фаза 2:  Веб-приложения
    Фаза 3:  keycloak, zookeeper, rabbitmq
    Фаза 4:  postgres

Deployment hash
----------------

При команде ``reload`` лаунчер использует механизм, аналогичный ``docker-compose up``:

1. Для каждого приложения вычисляется **deployment hash** на основе:

   - Docker-образа (image + tag)
   - Переменных окружения
   - Смонтированных томов
   - Портов
   - Лимитов ресурсов
   - Зависимостей

2. Hash сравнивается с hash работающего контейнера.

3. **Только изменённые контейнеры** пересоздаются -- неизменённые продолжают работать без прерывания.

Заранее увидеть, какие контейнеры будут пересозданы и почему, можно командой ``citeck reload --dry-run`` (или ``citeck diff``).

.. note::

    Если новая версия лаунчера меняет способ генерации контейнеров, после обновления соответствующие контейнеры пересоздаются **один раз**. Это указывается в заметках к выпуску (например, в 2.10.0 при первом запуске пересоздавались все контейнеры).

Обновление CLI и демона
------------------------

Установку CLI и демона обновляет тот же ``install.sh``, что и первичная
установка -- он определяет факт наличия предыдущей версии и переключается
в режим обновления:

.. code-block:: bash

    curl -fsSL https://github.com/Citeck/citeck-launcher/releases/latest/download/install.sh | bash

Команда ``citeck update`` бинарный файл **не обновляет** -- она обновляет только определения workspace и бандлов (см. :ref:`server_commands`).

При обновлении бинарного файла лаунчера:

1. Установщик показывает установленную и новую версии и запрашивает подтверждение.
2. Создаётся резервная копия текущего бинарного файла (``/usr/local/bin/citeck.bak``).
3. Демон останавливается в режиме **detach** (``citeck stop --shutdown --leave-running``): процесс демона завершается, но контейнеры Docker продолжают работать.
4. Новый бинарный файл копируется в ``/usr/local/bin/citeck``.
5. Запускается новый демон, который **подхватывает** работающие контейнеры через сравнение deployment hash.

.. code-block:: text

    Старый демон                     Новый демон
    +-----------+                    +-----------+
    | daemon v1 |  --detach-->       | daemon v2 |
    +-----------+  (containers       +-----------+
         |          stay running)         |
    +----v----+                      +----v----+
    | Docker  |  =================>  | Docker  |
    | Engine  |  (контейнеры         | Engine  |
    +---------+   сохранены)         +---------+

**Что происходит с приложениями** зависит от того, изменился ли их
``deployment hash`` (см. раздел «Deployment hash» выше):

- **Hash приложения не изменился** (новая версия CLI не меняет формат
  generator-а для этого типа приложения) -- контейнер продолжает работать
  без перезапуска. *Это типичный сценарий zero-downtime-обновления*.
- **Hash приложения изменился** (например, новая версия лаунчера добавила
  переменную окружения или том) -- соответствующие контейнеры
  пересоздаются. Ожидаемое время простоя по каждому такому приложению --
  от 1 до 5 минут (зависит от типа сервиса; Java-приложения дольше).

.. note::

    Чтобы заранее узнать, какие приложения будут пересозданы, после
    обновления бинарника выполните ``citeck reload --dry-run``. Команда
    покажет список контейнеров с изменённым hash до того, как вы их
    фактически перезапустите.

Если демон старой версии не смог сохранить состояние namespace перед остановкой, обновление прерывается **до** замены бинарного файла -- перезапустите прежнюю версию (``systemctl restart citeck``), она подхватит работающие контейнеры.

Если обновление прошло неудачно, используйте откат:

.. code-block:: bash

    citeck install --rollback

Это восстановит бинарный файл из ``.bak`` и перезапустит демон.
Контейнеры Docker не затрагиваются.

Интеграция с systemd
---------------------

Лаунчер автоматически создаёт systemd-сервис при установке:

**Unit-файл:** ``/etc/systemd/system/citeck.service``

Основные характеристики:

- **Restart=on-failure** -- автоматический перезапуск при сбое демона
- Контейнеры Docker продолжают работать при перезапуске демона
- Новый экземпляр демона подхватывает работающие контейнеры через hash matching
- При обновлении используется runtime drop-in (``/run/systemd/system/citeck.service.d/no-restart.conf``), чтобы systemd не перезапустил старый демон в момент замены бинарного файла

**Управление через systemd:**

.. code-block:: bash

    # Статус сервиса
    systemctl status citeck

    # Логи демона через journald
    journalctl -u citeck -f

    # Перезапуск (контейнеры сохраняются)
    systemctl restart citeck

.. warning::

    Не используйте ``systemctl stop citeck`` для остановки платформы. Это остановит только демон, но не контейнеры. Используйте ``citeck stop --shutdown``.

Управление секретами
---------------------

Секреты хранятся с шифрованием **AES-256-GCM** в директории ``/opt/citeck/conf/secrets/``.

**Типы секретов:**

- **Системные** -- генерируются автоматически:

  - JWT-ключ для подписи токенов
  - OIDC client secret для интеграции с Keycloak
  - Пароль администратора — для пользовательского входа (ecos-app realm)
  - Пароль сервисной УЗ ``citeck`` — для внутренних операций с Keycloak
  - Пароли для RabbitMQ и PgAdmin

- **Пользовательские** -- задаются через ``citeck setup``:

  - Пароль SMTP
  - Secret key для S3
  - Учётные данные Docker-реестра

- **Секреты workspace** (с версии 2.15) -- значения секретов, объявленных в разделе ``secrets:`` конфигурации workspace (например, пароль базы observer). Namespace сохраняет своё значение при первом использовании и дальше хранит его сам (см. :ref:`server_configuration`).

Каждый секрет шифруется отдельно. Мастер-пароль используется для вывода ключей шифрования (Argon2id; секреты, зашифрованные старыми версиями, читаются через PBKDF2-HMAC-SHA256).

Проверить согласованность хранилища системных секретов (без изменений) можно командой ``citeck diagnose --secrets``.

Реконсилер
-----------

Реконсилер -- фоновый процесс, работающий в демоне, который обеспечивает соответствие желаемого и фактического состояния контейнеров:

1. **Периодическая проверка** (по умолчанию каждые 60 секунд): сравнивает конфигурацию с реальным состоянием Docker.

2. **Liveness-проверки** (по умолчанию каждые 10 секунд): выполняет проверку живости приложения. Контейнер перезапускается только после **около 60 секунд непрерывных** неудач, поэтому длинная пауза сборки мусора не приводит к перезапуску. Перед перезапуском снимается дамп потоков (см. :ref:`server_jvm_diagnostics`).

3. **Автовосстановление**: при обнаружении упавшего контейнера инициирует повторный запуск с экспоненциальным backoff (от 1 до 10 минут).

Приложения, остановленные вручную (``citeck stop <app>``), реконсилер не трогает.

Настройка через ``/opt/citeck/conf/daemon.yml``:

.. code-block:: yaml

    reconciler:
      interval: 60            # секунды
      livenessPeriod: 10000   # миллисекунды
      livenessEnabled: true

Версии инфраструктуры
----------------------

Версии PostgreSQL, RabbitMQ, ZooKeeper, Keycloak, MongoDB и Qdrant привязаны к данным namespace: обновление бандла не переводит их на несовместимую версию автоматически. Перенос данных на новую версию и откат выполняются командами ``citeck deps upgrade`` и ``citeck deps rollback`` -- подробнее в :ref:`server_dependencies`.
