Версии инфраструктуры и их обновление
======================================

Начиная с версии **2.12** лаунчер привязывает версии инфраструктурных компонентов (PostgreSQL, RabbitMQ, ZooKeeper, Keycloak, MongoDB, Qdrant) к **данным** namespace. Обновление бандла больше не может молча перевести такой компонент на версию, несовместимую с уже существующими данными: лаунчер продолжает работать на той версии, на которой данные были созданы, сообщает о доступной новой версии и выполняет перенос данных только по команде администратора.

.. contents::
    :local:
    :depth: 2

Как это работает
-----------------

- **Пин версии.** Для каждой зависимости лаунчер запоминает версию, на которой реально работают её данные. Если бандл предлагает более новую версию, она не применяется, а показывается как доступное обновление (в ``citeck status`` -- строка ``Deps:``, подробности -- в ``citeck deps``).
- **Мелкие обновления** (патч-версии, не требующие переноса данных) применяются при следующем запуске namespace.
- **Понижение версии не выполняется.** Если бандл предлагает версию **старше** той, на которой работают данные, лаунчер сообщает об этом и оставляет данные на текущей версии.
- **Переходы, запрещённые разработчиком компонента,** не выполняются за один шаг. Например, RabbitMQ следует собственной матрице обновлений (4.1 → 4.3 напрямую недопустимо), Qdrant гарантирует чтение своего хранилища только через **один** минор. В таких случаях лаунчер называет промежуточную версию, через которую нужно пройти. Данные ZooKeeper старше 3.5 не переносятся.
- **Бандл может описать путь обновления списком версий** в разделе ``dependencies:``: последняя версия -- цель, предыдущие -- промежуточные ступени, которые лаунчер проходит в рамках одной миграции.

Новые namespace по-прежнему создаются на версиях, которые назначает бандл; пин влияет только на существующие данные.

Если данных нет — у зависимости нет контейнера, а её том удалён (например, вручную), — защищать нечего: применяется версия бандла, и обновление не предлагается. Если том существует (даже пустой), Docker не ответил или миграция не завершена, прежняя версия остаётся закреплённой.

Кроме встроенных зависимостей, в список попадают кластеры PostgreSQL и хранилища Qdrant, объявленные в конфигурации workspace (``additionalApps`` с ``type: POSTGRES`` или ``type: QDRANT``, например база observer -- ``observer-postgres``, см. :ref:`server_configuration`). Они получают тот же пин версии, миграцию и откат.

.. note::

    Keycloak и MongoDB отображаются в списке, но их обновление пока не выполняется -- лаунчер только сообщает о доступной версии.

Просмотр: citeck deps
----------------------

.. code-block:: bash

    citeck deps
    # или
    citeck deps list

Команда выводит таблицу: зависимость, текущая версия (на которой работают данные), версия, предлагаемая бандлом, и статус. Возможные статусы:

.. list-table::
    :widths: 35 65
    :header-rows: 1
    :class: tight-table

    * - Статус
      - Значение
    * - актуальна
      - Данные работают на версии из бандла
    * - ``<версия>`` применится при следующем запуске
      - Обновление не требует переноса данных
    * - доступно обновление
      - Требуется миграция: ``citeck deps upgrade <зависимость>``
    * - доступно обновление, нужна более новая версия лаунчера
      - Этот лаунчер ещё не умеет переносить данные на предложенную версию -- обновите лаунчер (см. :ref:`server_architecture`, раздел «Обновление CLI и демона»)
    * - обновление заблокировано
      - Переход не поддерживается за один шаг; причина и промежуточная версия выводятся под таблицей
    * - бандл предлагает более старую версию
      - Данные остаются на текущей версии

Под таблицей выводятся также: доступный откат, идущая миграция и результат последней миграции или отката.

Для автоматизации используйте ``citeck deps --format json``.

Миграция: citeck deps upgrade
------------------------------

.. code-block:: bash

    citeck deps upgrade <зависимость> [flags]

**Флаги:**

.. list-table::
    :widths: 30 70
    :header-rows: 1
    :class: tight-table

    * - Флаг
      - Описание
    * - ``-d``, ``--detach``
      - Запустить миграцию и сразу вернуть управление
    * - ``--replace-existing``
      - Разрешить удаление целевого тома, оставшегося от предыдущей попытки
    * - ``--yes``
      - Не запрашивать подтверждение (глобальный флаг)

**Примеры:**

.. code-block:: bash

    # PostgreSQL 17 -> 18
    citeck deps upgrade postgres

    # RabbitMQ, ZooKeeper, Qdrant
    citeck deps upgrade rabbitmq
    citeck deps upgrade zookeeper
    citeck deps upgrade qdrant

    # База observer
    citeck deps upgrade observer-postgres

Порядок работы:

1. **Предварительные проверки** -- версия данных, допустимость перехода, свободное место на диске, наличие целевого тома. Результат выводится на экран, после чего запрашивается подтверждение. Если проверки не пройдены, ничего не меняется.
2. **Остановка namespace.** Namespace останавливается на всё время миграции -- планируйте её в технологическое окно.
3. **Перенос данных в новый том:**

   - **PostgreSQL** -- полный дамп (``pg_dumpall``) из текущего кластера, создание нового кластера в **новом** томе, восстановление, сверка списка баз, ролей и числа таблиц. Дамп временно пишется в ``/opt/citeck/data/runtime/<namespace>/deps-migration/``. Требуется свободное место примерно на два объёма данных.
   - **RabbitMQ, ZooKeeper, Qdrant** -- том с данными копируется, обновляется **копия**; исходный том только читается. Для Qdrant дополнительно сверяются коллекции, алиасы и количество точек, а перед каждым шагом версии лаунчер ждёт завершения оптимизации коллекций (до 30 минут) и прерывает миграцию, если оптимизатор сообщает об ошибке.

4. **Переключение** namespace на новый том и новую версию, после чего namespace запускается снова (если работал до миграции).

Любой сбой на шагах 3--4 автоматически откатывает изменения: namespace остаётся на прежней версии и прежних данных.

Миграция выполняется в демоне: закрытие терминала или ``Ctrl+C`` прекращает только вывод прогресса, но не саму миграцию. Результат смотрите в ``citeck deps``.

.. note::

    Пока идёт миграция (или создание снимка), запуск, перезагрузка и удаление namespace отклоняются с сообщением о том, какая операция выполняется.

.. note::

    ``citeck deps upgrade`` отказывает, если namespace находится в статусе ``STALLED`` (например, приложение ждёт остановленную вручную зависимость). Сначала запустите остановленное приложение: ``citeck start <app>``.

Тома данных
~~~~~~~~~~~~

Тома данных нумеруются по миграциям: успешная миграция помещает данные в следующий том (например, ``rabbitmq2`` → ``rabbitmq3``). Тома находятся в ``/opt/citeck/data/runtime/<namespace>/volumes/``.

**Прежний том после успешной миграции сохраняется** -- он нужен для отката. Удалите его вручную, когда убедитесь в работоспособности новой версии. ``citeck clean`` такие тома не удаляет: он работает только с ресурсами namespace, которых больше не существует.

Если целевой том остался от предыдущей неудачной попытки, предварительная проверка покажет его размер и версию; удалить его можно только явно -- флагом ``--replace-existing``.

Откат: citeck deps rollback
----------------------------

.. code-block:: bash

    citeck deps rollback <зависимость> [flags]

**Флаги:**

.. list-table::
    :widths: 30 70
    :header-rows: 1
    :class: tight-table

    * - Флаг
      - Описание
    * - ``-d``, ``--detach``
      - Запустить откат и сразу вернуть управление
    * - ``--yes``
      - Не запрашивать подтверждение (глобальный флаг)

Откат возвращает зависимость на версию и **тот том с данными**, на которых она работала до последней миграции. Namespace останавливается и запускается снова. Ничего не создаётся и не удаляется.

.. warning::

    Всё, что записано после миграции, остаётся в томе, который namespace покидает, и **больше не читается**. Вернуться вперёд после отката нельзя. Откат делается на один шаг.

Откат доступен, только если миграцию выполнил этот лаунчер и сохранённый том ещё существует. ``citeck deps`` показывает строку «Доступен откат», когда он возможен.

Отчёты о миграциях
-------------------

Каждая миграция и каждый откат, а также обновление, отклонённое предварительными проверками, записывают текстовый отчёт в ``/opt/citeck/logs/reports/``: что переносилось, пройденные шаги, итог и -- при сбое -- логи временных контейнеров, снятые до отката. Хранятся 50 последних отчётов. Отчёты автоматически включаются в архив ``citeck dump-system-info`` (см. :ref:`server_support_dump`).

Ручная смена версии зависимости
--------------------------------

Образ зависимости можно явно задать через ``citeck edit <зависимость>``. Такая правка:

- **отклоняется**, пока есть данные, которые выбранная версия не примет, -- в сообщении указано, есть ли путь назад (сохранённый том);
- **разрешена**, если том с данными удалён (сохранять нечего), -- лаунчер запоминает выбранную версию;
- **всегда отклоняется** для версии ниже минимальной поддерживаемой (PostgreSQL 17, RabbitMQ 4.1, ZooKeeper 3.9, Keycloak 26.4, MongoDB 4, Qdrant 1.14).

На существующих данных лаунчер не переводит зависимость на более старую версию, включая откат патч-версии.
