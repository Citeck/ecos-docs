Версионирование контента
=========================

.. contents::
   :depth: 3

**Версионирование контента** — механизм, при котором каждая замена основного файла записи сохраняет предыдущее состояние файла в отдельную запись версии. Благодаря этому доступны просмотр и скачивание любой из предыдущих версий документа, а также сравнение версий между собой.

Пользовательский интерфейс механизма — :ref:`виджет «Журнал версий» <widget_versions_journal>` и функция :ref:`сравнения версий <version_comparison>`.

Включение версионирования
--------------------------

Версионирование включается добавлением :ref:`аспекта <aspects_user>` **«Версионируемый»** (``versionable``) к :ref:`типу данных <data_types>`:

.. code-block:: yaml

   aspects:
     - ref: emodel/aspect@versionable

Аспект не содержит атрибутов — он служит признаком того, что для записей типа нужно вести версии.

Версионирование можно временно отключить, не снимая аспект с типа, — через конфигурацию аспекта:

.. code-block:: yaml

   aspects:
     - ref: emodel/aspect@versionable
       config:
         disabled: true

Аспект «Версионные данные»
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Аспект **«Версионные данные»** (``versionable-data``, префикс ``version``) добавляется к записи автоматически при первой записи основного контента, если тип версионируемый. Он хранит служебные данные текущей версии:

.. list-table::
      :widths: 10 10 30
      :header-rows: 1
      :class: tight-table

      * - Атрибут
        - Название
        - Описание
      * - ``version:version``
        - Версия
        - Номер актуальной версии записи. Если не задан, считается равным ``1.0``.
      * - ``version:comment``
        - Комментарий
        - Комментарий к актуальной версии.
      * - ``version:versions``
        - Версии
        - Дочерняя ассоциация на записи предыдущих версий.

Что хранится в версии
----------------------

Предыдущие версии сохраняются как отдельные записи системного типа ``record-version``. Данные размещаются в таблице ``ecos_record_version`` в той же схеме БД, что и сама версионируемая запись.

.. list-table::
      :widths: 10 10 30
      :header-rows: 1
      :class: tight-table

      * - Атрибут
        - Тип
        - Описание
      * - ``_parent``
        - ASSOC
        - Ссылка на версионируемую запись. ``_parentAtt`` — ``version:versions``.
      * - ``content``
        - CONTENT
        - Файл версии.
      * - ``name``
        - MLTEXT
        - Имя файла на момент создания версии.
      * - ``version``
        - TEXT
        - Номер версии.
      * - ``comment``
        - TEXT
        - Комментарий к версии.
      * - ``versionCreator``
        - PERSON
        - Автор версии.
      * - ``versionCreated``
        - DATETIME
        - Дата и время создания версии.

.. note::

   Запись версии ссылается на ту же запись контента, которая была у документа до замены файла, — физически файл при создании версии не копируется.

.. important::

   В версии сохраняются только файл и перечисленные выше метаданные. **Значения остальных атрибутов записи в версию не попадают.** Для отслеживания изменений атрибутов используется история событий (аспект ``history-config``).

Когда создаётся версия
-----------------------

Версия создаётся при сохранении записи, если одновременно выполняются условия:

* к типу записи применён аспект «Версионируемый» и он не отключён через ``disabled``;
* изменился **основной атрибут контента** записи (сравниваются ключ данных и хранилище) либо явно изменено значение ``version:version``;
* до изменения у записи уже был контент — иначе версия не создаётся (первая загрузка файла версию не порождает).

В версию сохраняется **предыдущее** состояние файла; актуальный файл всегда остаётся в самой записи. В журнале версий актуальная версия формируется на лету из текущего контента записи и в таблицу версий не пишется.

.. note::

   Версионируется только основной атрибут контента типа (тот, что доступен через ``_content``, см. :ref:`конфигурацию контента <datatypes_content>`). Файлы в дополнительных атрибутах с типом «Содержимое» не версионируются.

Нумерация версий
-----------------

* Номер первой версии — ``1.0``.
* Значение с префиксом ``+`` задаёт относительный инкремент: ``+0.1`` — минорная версия, ``+1.0`` — мажорная.
* Можно задать номер абсолютным значением, но только больше текущего. Попытка понизить версию завершается ошибкой ``Version downgrading is not supported``.

Работа с версиями через API
----------------------------

Загрузка новой версии (REST)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: text

   POST /gateway/emodel/api/content-version/upload

.. list-table::
      :widths: 10 30
      :header-rows: 1
      :class: tight-table

      * - Параметр
        - Описание
      * - ``filedata``
        - Файл новой версии.
      * - ``updateNodeRef``
        - Ссылка на версионируемую запись.
      * - ``description``
        - Комментарий к версии (необязательный).
      * - ``majorversion``
        - ``true`` — мажорная версия (``+1.0``), иначе минорная (``+0.1``).

Перед загрузкой проверяются право ``Write`` на запись, признак защиты контента от изменения, а также состояние блокировки документа: если документ редактируется в редакторе документов или заблокирован другим пользователем, загрузка отклоняется.

Загрузка новой версии через мутацию записи
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

REST-метод выше — обёртка над обычной мутацией записи, поэтому создать версию можно и напрямую через :ref:`Records API <Records_API>`:

.. code-block:: kotlin

   recordsService.mutate(
       recordRef,
       mapOf(
           "version:version" to "+0.1",
           "version:comment" to "Комментарий к версии",
           "_content" to tempFileRef
       )
   )

Получение списка версий
~~~~~~~~~~~~~~~~~~~~~~~~

Список версий запрашивается у источника ``version``, который сам определяет, где хранятся версии конкретной записи:

.. code-block:: json

   {
     "query": {
       "sourceId": "version",
       "query": { "record": "emodel/document@some-id" }
     },
     "attributes": {
       "version": "version",
       "modified": "modified",
       "modifier": "modifier?disp",
       "comment": "comment",
       "name": "name",
       "downloadUrl": "downloadUrl"
     }
   }

Результат отсортирован от новых версий к старым, первой в списке идёт актуальная версия записи.

Скачать файл конкретной версии можно по ссылке из атрибута ``downloadUrl``:

.. code-block:: text

   /gateway/emodel/api/ecos/webapp/content?ref=record-version@<id версии>&att=content

Создание записи версии напрямую
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Записи версий можно создавать напрямую в источнике ``record-version``. Это основной сценарий для миграции данных из внешних систем, когда нужно сохранить исходных авторов и даты версий:

.. code-block:: kotlin

   recordsService.create(
       "record-version",
       mapOf(
           "_parent" to recordRef,
           "_parentAtt" to "version:versions",
           "version" to "1.0",
           "comment" to "Перенесено из внешней системы",
           "versionCreator" to EntityRef.create("emodel", "person", "ivanov"),
           "versionCreated" to Instant.parse("2019-05-14T10:15:30Z"),
           "_content" to tempFileRef
       )
   )

.. warning::

   Источник ``record-version`` допускает только создание и удаление записей версий. Мутация уже существующей записи версии игнорируется.

Сравнение версий
-----------------

Сравнение выполняется источником ``version-diff``:

.. code-block:: json

   {
     "query": {
       "sourceId": "version-diff",
       "query": {
         "first": "record-version@<id первой версии>",
         "second": "record-version@<id второй версии>"
       }
     },
     "attributes": { "diff": "diff" }
   }

В атрибуте ``diff`` возвращается HTML-разметка, в которой добавленные и удалённые фрагменты выделены отдельными классами.

Обе сравниваемые версии должны принадлежать одному источнику и иметь одинаковый формат.

Как работает сравнение
~~~~~~~~~~~~~~~~~~~~~~~

Из каждой версии извлекается текст, после чего выполняется посимвольное сравнение двух текстов:

* файлы текстовых форматов читаются напрямую;
* остальные форматы конвертируются в текст микросервисом ``ecos-transformations`` (конвертация выполняется через OnlyOffice).

Поддерживаемые форматы
~~~~~~~~~~~~~~~~~~~~~~~

.. list-table::
      :widths: 15 30
      :header-rows: 1
      :class: tight-table

      * - Группа
        - Форматы
      * - Текстовые (без конвертации)
        - ``txt``, ``csv``, ``json``, ``xml``, ``yaml``, ``html``, ``sql``, ``sh``, ``js``, ``css``
      * - Документы (через конвертацию)
        - ``doc``, ``docx``, ``odt``, ``pdf``

.. note::

   Сравнение является текстовым: форматирование, таблицы, изображения и разметка документа не сравниваются. Для файлов, из которых нельзя извлечь текст (изображения, сканы, в том числе PDF без текстового слоя, архивы), а также для форматов ``xls``/``xlsx`` и ``ppt``/``pptx`` сравнение недоступно.

   Перечень форматов расширяем: добавить можно любой формат, для которого поддерживается конвертация в текст.

Хранение файлов версий
-----------------------

Файлы версий хранятся так же, как и основной контент записи, — в хранилище, заданном в :ref:`конфигурации контента типа <datatypes_content>`. По умолчанию используется локальное хранилище (БД), для больших объёмов подключается S3 (см. :ref:`смену типа хранилища <type_content_storage>` и :ref:`Content микросервис <content_service>`).

При удалении записи версии физический файл удаляется из хранилища только в том случае, если на него не осталось ссылок из других записей контента.

Права доступа
--------------

Тип ``record-version`` использует политику прав ``PARENT`` — права на версию наследуются от версионируемой записи. Список версий возвращается только при наличии права ``Read`` на саму запись; сам запрос к хранилищу версий после проверки прав выполняется в системном контексте.

Для типа ``record-version`` отключено ведение истории событий (аспект ``history-config``, параметр ``disableHistory``), чтобы создание версий не засоряло историю изменений документа.

Ограничения
------------

* Версионируется только основной атрибут контента типа; дополнительные атрибуты с типом «Содержимое» не версионируются.
* Значения атрибутов записи в версии не сохраняются — версионируется только файл.
* Сравнение версий доступно только для форматов, из которых можно извлечь текст, и является текстовым.
* Изменение уже созданной записи версии через API не выполняется.
* Назначение предыдущей версии актуальной (откат) не поддерживается. Чтобы вернуться к предыдущему состоянию документа, нужно скачать файл нужной версии и загрузить его как новую версию.
* Автор и дата версии определяются по метаданным загруженного файла, то есть фиксируются текущий пользователь и время загрузки. Сохранить исходные значения (например, при миграции из внешней системы) можно только созданием записей версий напрямую в источнике ``record-version``.
