.. _ai-architecture:

Механика выполнения AI-агентов
==================================

.. contents::
    :depth: 2

Статья описывает, как платформа выполняет запросы к :ref:`AI-агентам <user-agents>`: движки выполнения, маршрутизацию, конвейер планирования и исполнения, точки участия человека, области публикации артефактов и ограничения выполнения.

Ключевой принцип
-----------------

**Структурные решения принимает код платформы, языковая модель отвечает за содержание.** Маршрутизация запроса, выбор области публикации, порядок этапов конвейера, проверка ссылок на артефакты и права доступа определяются детерминированным кодом. Модель генерирует содержимое — текст ответа, структуру артефакта, формулировку плана — внутри рамок, заданных кодом. Такой подход делает поведение агентов предсказуемым и позволяет использовать экономичные модели без потери надёжности.

Движки выполнения
------------------

Каждый агент выполняется одним из двух движков — поле ``engine`` записи агента:

**TOOL_LOOP — операционный диалоговый цикл.** Модель в цикле вызывает инструменты из белого списка агента (поиск записей, чтение документов, письма, изображения) и формирует ответ. Работает с памятью диалога, под правами текущего пользователя. Изменяющие операции (``mutateRecord``, ``deleteRecords``) выполняются только после подтверждения пользователем в диалоге. Инструмент ``deleteRecords`` не входит в белые списки поставляемых агентов — его можно добавить собственному агенту.

**CONFIG — агент конфигурирования платформы.** Тот же цикл с инструментами, но набор инструментов — генерация и публикация артефактов (типы данных, формы, процессы, журналы, шаблоны уведомлений, права, таблицы решений и другие виды — полный перечень см. в разделе :ref:`ai-pipeline`), правка скриптов и документация приложения. Ход работы отображается в чате пошаговой лентой выполняемых инструментов. Публикация артефактов при включённом ``requireDeployConfirmation`` требует подтверждения человеком.

Сгенерированный черновик артефакта хранится в диалоге до его успешной публикации. Если публикацию отклонили кнопкой «Отмена» или она завершилась ошибкой, черновик остаётся, и его можно доработать репликой вида «поправь … и разверни снова». После успешной публикации черновик удаляется: следующий запрос в том же диалоге на создание целого приложения уже не продолжает правку черновика, а уходит в конвейер планирования. В диалоге хранится один неопубликованный черновик каждого вида артефакта: если новый запрос заменяет его черновиком другого артефакта того же вида, ассистент сообщает об этом строкой в ответе — чтобы работать с несколькими артефактами одного вида, для каждого стоит начать отдельный диалог.

.. _ai-routing:

Маршрутизация
~~~~~~~~~~~~~~

#. Диалог с привязанным агентом обслуживается движком этого агента.
#. Чат без выбранного агента обслуживается операционным агентом по умолчанию (свойство ``citeck.ai.agents.default-operational``, по умолчанию ``tasks-documents-helper``).
#. Запрос конфигурации оценивается классификатором объёма: **один артефакт** остаётся в цикле агента конфигурирования; **проект из нескольких артефактов** (например, «создай приложение для учёта командировок») перенаправляется в конвейер планирования и исполнения.

Диагностика
~~~~~~~~~~~~

Ошибки конфигурации агента не маскируются: несуществующий агент, отключённый агент, неизвестный провайдер или движок дают понятное сообщение об ошибке с указанием причины, а не молчаливую подстановку значений по умолчанию.

.. _ai-pipeline:

Агентный конвейер: планирование и исполнение
---------------------------------------------

Многоартефактные запросы выполняются конвейером «план → утверждение → исполнение».

Планирование
~~~~~~~~~~~~~

Модель строит план из этапов с зависимостями (граф). Типы этапов: поиск артефактов, поиск в базе знаний и поиск в документации платформы (оба — только при включённом поиске), анализ артефакта, генерация артефакта, публикация. Проверка отдельным этапом не планируется: каждый этап генерации проверяет свой артефакт перед сохранением. Этап генерации — один на все поддерживаемые виды артефактов (тип данных, форма, процесс, журнал, сохранённый вид журнала, шаблон уведомления, действие над записью, права типа, права на запись, канбан-доска, карточка записи, патч артефакта, таблица решений); конкретный вид — поле этапа, а не отдельный тип этапа. План показывается пользователю со структурным предпросмотром: для типов данных — атрибуты, статусы и роли будущего артефакта; для форм и процессов — ключевые поля и шаги. Если запрос содержит то, что конвейер построить не может (например, отчёт нестандартного вида), это явно перечисляется в плане, а не подменяется другим типом артефакта.

Планировщик записывает состав каждого этапа полностью. Карточка плана показывает первые 10 строк этапа и строку с числом остальных; строки об удалении или замене («Удалить атрибуты: …», «Заменить статусы: …») видны всегда, чтобы при утверждении ничего не удалялось незаметно. В генерацию уходит полный список, а не только видимая часть.

**Что попадает в план, решает запрос, а не догадка кода.** Код не вычёркивает из плана этап только потому, что не нашёл в запросе упоминания этого вида артефакта:

- Этап вида, которого нет в записи требований, остаётся в плане, а карточка называет его строкой «Сверх запроса: <вид> — в требованиях, которые ассистент записал по вашему запросу, этого нет, шаг предложил планировщик. Если он не нужен, уберите его правкой плана.» Запись могла пропустить пункт спецификации: перед утверждением сравните план со своим запросом.
- Если пользователь прямо отказался от вида артефакта («без BPMN», «уведомления не нужны»), планировщик получает один корректирующий круг. Если этап всё же остался, карточка сообщает: «Вы просили без «<вид>», шаг оставлен планировщиком — уберите его правкой плана.» Перед утверждением попросите изменить план и проверьте его состав.
- Сам код убирает этапы только в перечисленных случаях: тип данных уже существует и этап ничего в нём не меняет (остальные артефакты плана привязываются к существующему типу); пользователь прямо просил тип не менять; вид артефакта не создаётся в текущем рабочем пространстве; вид артефакта может создавать только администратор (действие над записью в рабочем пространстве — администратор или менеджер этого пространства); в рабочем пространстве запланирована кнопка смены этапа; этап из рабочего пространства меняет глобальный артефакт или артефакт глобального типа; права типа относятся к типу другого рабочего пространства; перенос полей глобального типа направлен в тип, который в пространстве уже есть (см. :ref:`ai-deploy-scope`). В этих случаях итоговую строку над этапами пишет код: «В плане остаются шаги: …» и по одному предложению на каждую причину удаления, например «Тип «Договор» уже существует и используется как есть: шаг его изменения из плана убран. Если тип нужно изменить — скажите, что в нём поменять.»

.. _ai-requirements:

Разбор требований и уточняющие вопросы
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Перед построением плана бизнес-приложения модель разбирает запрос и приложенную спецификацию в единую запись требований: какие виды артефактов запрошены и от каких пользователь отказался, какие сущности, поля, этапы, роли и пожелания названы. Каждый пункт записи сопровождается дословной цитатой из текста пользователя; код сверяет цитату с тем, что пользователь действительно написал, и отбрасывает пункты, которых в его текстах нет. По этой записи проверяется, что план покрывает запрос. Текст приложенной спецификации и требования к сущности передаются и на этапы генерации: каждый этап получает требования своей сущности, а не только краткие строки плана.

- **Ответ на уточняющий вопрос и правка плана дополняют ту же запись**, а не запускают разбор заново. Новое добавляется, пункт, о котором ответ не говорит, сохраняется, а удаляется только то, что пользователь сам попросил убрать. Над планом выводится блок «ℹ️ После ваших ответов на вопросы в требованиях к приложению:» (после правки плана — «ℹ️ После вашей правки в требованиях к приложению:») с перечнем того, что добавлено, изменено, удалено и оставлено.
- **Сущности с одинаковыми названиями** в записи требований объединяются без отдельного вопроса; карточка плана сообщает об объединении. Если нужны две разные сущности, задайте им разные названия правкой плана.
- **Если внести ответ или правку в запись не удалось**, запись остаётся прежней, а карточка плана сообщает: «ℹ️ Не удалось внести ваш ответ в разбор требований: план построен по тексту ответа, а проверки пожеланий (виды, нумерация, этапы, права) работают по прежнему разбору.»
- **Сбой самого разбора не скрывается.** При сбое разбор автоматически повторяется один раз. Отказ провайдера в доступе (HTTP 401, 403), превышение лимита (HTTP 429) и другие ошибки запроса (4xx) не повторяются — карточка показывается сразу и говорит, что разбор запускался один раз. Карточка паузы предлагает «Повторить разбор», «Построить план без разбора» и «Отмена»; в системе к этому моменту ничего не изменено. План, построенный без разбора, начинается с предупреждения «⚠️ План построен без разбора ТЗ…»: проверки пожеланий по такому плану не работают. Если вместо нажатия кнопки отправить новое сообщение, карточка снимается.

Утверждение плана
~~~~~~~~~~~~~~~~~~

План исполняется только после утверждения человеком: кнопки «Подтвердить» и «Отклонить», свободным текстом — изменение плана или вопрос. Вопрос о плане получает ответ, после чего план предъявляется снова. См. сводную таблицу точек участия человека ниже.

.. _ai-collision:

Совпадение с существующими артефактами
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Отдельной карточки совпадений и вопроса о том, что делать с одноимённым артефактом, нет: решение принимает код, а карточка плана сообщает его строкой. Одноимённый артефакт ищется только в той области, куда пользователь может публиковать: в рабочем пространстве диалога или, при работе в глобальной области, среди глобальных артефактов.

Кнопки «Копировать» и «Наследоваться» не предлагаются; изменения задаются правкой плана. Если в области публикации несколько одноимённых артефактов, код выбирает один по постоянному правилу: артефакт, на который этап уже указывает своим идентификатором; иначе артефакт с идентификатором, который запланировал этап; иначе артефакт с самым коротким идентификатором, а при равной длине — первый по алфавиту, то есть исходный артефакт, а не его пронумерованные копии. Карточка плана называет выбор строкой «ℹ️ Взят «X» (<идентификатор>). Если нужен другой — напишите его id: <идентификаторы остальных>.», и утверждение плана изменяет именно названный артефакт.

- **Артефакт с таким названием уже есть в этой области** — этап плана изменяет его, второй такой же артефакт не создаётся. Карточка плана говорит: «ℹ️ <Вид> «X» уже есть — будет изменён: <что меняется>. Если нужен отдельный артефакт, назовите его по-другому.»
- **Одноимённый артефакт есть только в глобальной области, а работа идёт в рабочем пространстве** — это не совпадение: в пространстве создаётся свой артефакт, глобальный не меняется. Карточка говорит: «ℹ️ «X» (<вид>): в этом пространстве такого артефакта нет — создаётся новый артефакт пространства; одноимённый глобальный не меняется.»
- **Существующий тип используется как есть**, если пользователь не просил его менять или прямо сказал, что менять его не нужно: этап изменения типа код убирает, а остальные артефакты плана привязываются к существующему типу.
- **Новый артефакт никогда не занимает идентификатор существующего.** Правило действует для формы, журнала, кнопки (действия над записью) и шаблона уведомления, а в конвейере — и для процесса при его публикации. Если идентификатор занят, новый артефакт получает следующий свободный (например, с окончанием ``-2``), прежний остаётся без изменений, а карточка плана или итог этапа называет идентификатор, под которым артефакт создаётся, например «Кнопка с идентификатором «X» уже есть — новая кнопка будет создана как «X-2», прежняя останется без изменений.» Кнопка, у которой совпадают и идентификатор, и название, считается той же кнопкой: изменения вносятся в неё, и карточка говорит об этом. Чтобы изменить существующий артефакт, попросите об этом прямо или укажите его через @-упоминание.
- **Тип данных с тем же идентификатором, но с другим названием — это другой тип.** Если новая сущность из требований получила идентификатор, который в области записи уже занят типом с другим названием (например, типом другого приложения), новый тип получает следующий свободный идентификатор, а карточка плана говорит: «Тип с идентификатором «X» уже есть — новый тип будет создан как «X-2».» Существующий тип изменяется, только если совпадает и название, если пользователь назвал этот тип ссылкой, идентификатором или названием в кавычках либо если тип создан в этом же диалоге.

Исполнение
~~~~~~~~~~~

- Этапы выполняются с учётом зависимостей; независимые этапы одной волны могут выполняться параллельно. Каждый этап работает в изолированной памяти и получает результаты только тех этапов, от которых зависит.
- Ход исполнения отображается пошаговым индикатором с состоянием каждого этапа.
- Ошибка этапа предлагает выбор: **повторить**, **пропустить**, **отменить**. Перед этим генерация повторяется автоматически: модель получает ошибку проверки и пробует снова (до 3 повторов после первой попытки). Без повторов конвейер сразу останавливается и спрашивает человека, если сбой вызван недоступностью сервиса модели или отсутствием нужного типа данных либо генератор уже исчерпал собственные попытки. Публикация при ошибке всегда останавливается и спрашивает человека. Поисковые и аналитические этапы после 2 неудачных повторов пропускаются автоматически.
- Если генератор признал отказ окончательным, то есть повторная генерация дала бы тот же ответ, карточка сбоя не предлагает «Повторить» — остаются «Пропустить» и «Отменить», а просьба «повтори» в чате этап заново не запускает. Кнопка «Повторить» сохраняется, если отказ вызван тем, что сервисы платформы не ответили, что названного типа данных нет (его можно создать) или что артефакт, от которого зависит этап, ещё не развёрнут другим этапом плана.
- Если при генерации выясняется, что типу данных, от которого зависит артефакт, не хватает атрибутов, ролей, статусов или аспектов, конвейер останавливается и показывает карточку с перечнем недостающего и кнопками «Добавить поля и продолжить» (если не хватает ролей, статусов или аспектов — «Добавить в тип и продолжить»), «Пропустить генерацию» и «Отменить выполнение». При согласии в план добавляются этапы изменения и публикации типа, после чего заблокированный этап выполняется заново.
- Если недостающее нужно добавить в глобальный тип, а работа идёт в рабочем пространстве, карточка показывается без кнопки добавления: «ℹ️ Тип «X» — глобальный: из рабочего пространства он не меняется, поэтому недостающее в него не добавляется. Пропустите шаг или отмените выполнение; свой тип можно создать под другим названием.»
- Этап, который код снимает уже при исполнении, пропускается вместе со своей публикацией без повторов и без карточки сбоя; остальной план выполняется, а итог один раз объясняет, почему этап не выполнен. Так снимается, например, отдельный процесс напоминаний, который запускается по таймеру и не связан с записью, если процесс записи у типа уже есть или запланирован: письма ролям записи из такого процесса не ушли бы, поэтому итог предлагает добавить напоминания в процесс записи.
- План можно пересмотреть по ходу исполнения: выполненные этапы сохраняют статус и заново не выполняются — в частности, уже созданный тип не создаётся повторно и выполненная форма не дублируется. Этапы, которые правка изменила, генерируются и публикуются заново.

Правка артефактов и остановка генерации
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

При изменении существующего типа сохраняются атрибуты, статусы и роли, которых запрос не касается. Удаление атрибутов и замена списков статусов или ролей отражаются отдельными строками плана: «Удалить атрибуты: …», «Заменить статусы: …», «Заменить роли: …». Проверьте эти строки перед утверждением. Если правка типа не содержит изменений, ассистент сообщает об этом и возвращает исходную структуру.

Если план делает обязательными поля существующего типа, у которого уже есть записи (или проверить это не удалось), обязательность ставится не в тип, а в форму этого типа: обязательность в типе не дала бы сохранить уже существующие записи. Об этом говорит строка в итоге этапа, а при работе из глобального контекста — и строка на карточке плана. Если этап типа добавляет поля существующему типу или делает их обязательными, а шага формы этого типа в плане нет, код сам добавляет точечную правку главной формы типа, которая выполняется после публикации типа, и карточка плана говорит об этом строкой; если такой шаг добавить нельзя (например, форма вне области публикации или план уже на пределе числа этапов), строка называет причину.

Системные поля формы ``_statusModified``, ``_created``, ``_creator`` и ``_modified`` могут оставаться на форме только для чтения (``disabled``). Пользователь не должен заполнять их вручную.

Нехватка атрибута, роли, статуса, аспекта или связанного артефакта может остановить генерацию до получения черновика. В диалоге ассистент сообщает, чего не хватает и как продолжить: сначала дополнить и опубликовать зависимый тип либо найти или создать связанный артефакт, затем повторить генерацию. В конвейере для расширения типа показывается карточка с решением пользователя, описанная ниже. Разрешение продолжить не отменяет ограничений области публикации и прав доступа.

.. _ai-deploy-scope:

Область публикации
-------------------

Публикация артефакта всегда выполняется в определённую **область**: глобально или в рабочее пространство. Область показывается в карточке подтверждения публикации.

Правила определяются кодом платформы:

- **Из рабочего пространства** (именованного или личного) публикация всегда идёт в это рабочее пространство. Запросить публикацию глобально из рабочего пространства нельзя — попытка переопределить область отклоняется с объяснением, а не подменяется молча.
- **Где какой вид артефакта можно создать — это настройка, а не поведение кода.** Список видов, допустимых внутри рабочего пространства, задаётся свойством ``citeck.ai.artifacts.workspace-creatable`` (по умолчанию: тип данных, форма, процесс, журнал, шаблон уведомления, карточка записи, канбан-доска, таблица решений, права типа, патч артефакта, действие над записью). Проверку ведёт один компонент, и она применяется одинаково в диалоге, в этапе конвейера, при проверке плана и при публикации. Права типа, созданные внутри пространства, получают идентификатор вида ``<пространство>:<идентификатор>``; патч разрешён только над артефактами своего пространства; настройки журнала и права на запись создаются только глобально.
- **Действие над записью (кнопка на карточке) в рабочем пространстве** сохраняется как действие этого пространства и привязывается к типу пространства. Создавать и изменять такие действия могут администратор платформы и менеджер рабочего пространства; другому пользователю ассистент отказывает до обращения к платформе и советует попросить менеджера пространства или администратора. Глобальные действия создаёт и изменяет только администратор платформы. В рабочем пространстве доступны кнопки, которые создают запись, скачивают документ по шаблону, открывают ссылку или изменяют обычное поле записи. Кнопка смены этапа (статуса) в рабочем пространстве в этой версии не создаётся — ни планом, ни отдельным запросом: этап записи меняет её процесс, и карточка плана говорит об этом. Журнал или канбан-доска пространства не может ссылаться на действие другого рабочего пространства. Для действий в пространстве нужна версия ``ecos-uiserv``, которая их поддерживает (2.41 и новее); более ранняя версия сохраняет действие глобальным, и ассистент предупреждает, что кнопка к типу не привязана, а глобальное действие нужно проверить или удалить.
- **Кнопка «Создать …»** (действие создания записи) на платформе всегда открывает форму создания: значения из настроек кнопки подставляются в форму, а запись сохраняется, когда пользователь нажмёт «Сохранить». Ассистент сообщает об этом строкой.
- **Записи нового типа данных всегда можно создать из интерфейса.** Если сгенерированный тип отключает вариант создания по умолчанию и не задаёт собственных вариантов, код снимает этот запрет: иначе у типа не было бы ни кнопки «Создать» в журнале, ни пункта меню, ни кнопки в окне выбора. Кто может создавать записи, определяет матрица прав. В поле выбора записи, список которого отфильтрован по другому полю формы, кнопка создания скрывается: окно выбора передаёт в форму создания только рабочее пространство, и созданная там запись не попала бы в отфильтрованный список. Ассистент сообщает об этом строкой.
- **Из рабочего пространства ассистент изменяет только артефакты этого пространства.** Глобальный артефакт из рабочего пространства не изменяется, не копируется и не наследуется; глобальный тип можно только использовать — например, как цель связи. Идентификатор без префикса пространства означает артефакт пространства: если такой артефакт в пространстве есть, он изменяется, если нет — создаётся новый. Просьба изменить глобальный артефакт (названный ссылкой или через @-упоминание) отклоняется с объяснением: в диалоге с агентом конфигурирования — ответом, в конвейере планирования — строкой на карточке плана, а этап из плана убирается. В диалоге ассистент предлагает два пути: создать в пространстве свой артефакт под другим названием или выполнить изменение из административного рабочего пространства.
- **Форма, журнал, канбан-доска и действие над записью для типа вне рабочего пространства** не создаются: такой артефакт привязывается к типу и изменил бы тип для всех, кто им пользуется. Карточку записи над глобальным типом конвейер создаёт как собственную карточку пространства.
- **Процесс над глобальным типом** создаётся в пространстве, только если записи этого типа принадлежат рабочим пространствам (как правило, это типы документов): для записей пространства будет запускаться процесс пространства вместо глобального, и карточка плана говорит об этом. Если записи типа к пространству не привязаны (как правило, это справочники), процесс пространства для них никогда бы не запустился, поэтому такой этап отклоняется до генерации.
- **Права типа не выходят за пределы рабочего пространства.** Платформа ищет права по типу без учёта пространства, поэтому матрица прав над глобальным типом или над типом другого пространства изменила бы доступ к его записям для всех пользователей системы. Такая матрица отклоняется до генерации, а в конвейере её этап убирается из плана со строкой на карточке. Права типа и права на запись вообще создаёт и меняет только администратор платформы: для других пользователей этапы этих видов убираются из плана, а в диалоге запрос отклоняется до обращения к модели.
- **Новый тип данных никогда не наследует другой тип.** Родителем нового типа может быть только базовый тип платформы (``case``, ``data-list`` или ``user-base``). Существующий дочерний тип при изменении сохраняет своего родителя.
- **Поля глобального типа переходят в новый тип только по прямой просьбе** пользователя — например, «свой справочник с такими же полями, как у глобального «Контрагент»». Тогда в пространстве создаётся новый тип с базовым родителем, а поля, статусы и этапы глобального типа переносит код в том виде, в каком они хранятся в системе; аспекты глобального типа подключаются к новому типу. Если пользователь назвал свои этапы, переносятся только они. Ответ сообщает о переносе отдельной строкой. Без такой просьбы новый тип не получает поля глобального молча: если модель пересказала поля глобального типа, которых пользователь не называл, они снимаются со строкой об этом. Перенос в тип, который в пространстве уже есть, не выполняется: такой этап снимается из плана.
- **Способ изменения существующего артефакта выбирает код**, а не модель: артефакт, созданный в этом диалоге, изменяется напрямую; артефакт, созданный или изменённый пользователем в доступной для записи области, — на месте; артефакт, поставляемый приложением, — патчем.
- **Администратор в глобальном административном рабочем пространстве** (``admin$workspace``) публикует глобально, изменяя артефакт на месте. Администратору, работающему в обычном рабочем пространстве, диалог подсказывает перейти в административное пространство, если нужно изменить оригинал.
- **Общий (глобальный) тип из глобального административного контекста** дорабатывается на месте: новый глобальный тип рядом с ним создаётся только по прямой просьбе. Такой тип используется во всех рабочих пространствах, поэтому карточка плана предупреждает о последствиях. Если новая форма станет главной формой общего типа, карточка говорит, что все записи типа (и его дочерних типов без своей формы) во всей системе будут открываться новой формой. Если план содержит матрицу прав над общим типом, карточка говорит, что матрица заменит права всех записей типа во всей системе. Форму или матрицу можно убрать из плана ответом на карточку.
- **Нехватка прав** на публикацию даёт одно понятное сообщение без цикла повторных попыток.

**Матрицы прав создаёт администратор платформы.** Для остальных пользователей этапы прав типа и прав на запись убираются из плана с объяснением. Статус менеджера рабочего пространства сам по себе не даёт права создавать матрицы. Если приложение требует настройки доступа, попросите администратора выполнить эту часть.

**Роль «Администратор» в сгенерированном типе** получает определённых исполнителей: в типе рабочего пространства — менеджеров этого пространства, в глобальном типе — группу администраторов платформы (``GROUP_ECOS_ADMINISTRATORS``). Отдельное поле для выбора администратора появляется только по прямой просьбе пользователя. Это правило относится к общей административной роли; бизнес-роли вроде «Администратор переговорных» сохраняют собственный смысл и настройку исполнителей.

**Итог публикации пишет код.** После подтверждённой публикации в диалоге с агентом конфигурирования сообщение о результате составляет код по развёрнутому артефакту, а не модель по памяти: где развёрнут артефакт («Форма «X» развёрнута в рабочем пространстве «Y»» или «… развёрнут глобально») и его структура. Попутные изменения типа называются отдельной строкой:

- действие, привязанное к типу, — «В тип «X» добавлено действие «Y»»;
- новая форма становится главной формой типа, только если у типа ещё нет своей формы или пользователь прямо попросил об этом. Карточка подтверждения сообщает об этом до публикации (например, «При развёртывании главная форма типа изменится: эта форма станет главной, и карточка записи будет открываться ею»), итог после публикации — строкой «Форма «X» стала главной формой типа «Y»».

Если после успешной публикации ассистент не смог продолжить работу над запросом (например, создать следующую форму), сообщение говорит: «⚠️ Развёртывание выполнено, но продолжить работу над запросом после него не удалось (<причина>)…» и просит повторить оставшиеся шаги отдельным сообщением. Недоступностью модели причина называется, только если сбой произошёл при обращении к модели; сбой сети при обращении к сервисам платформы так не называется — тогда причина записывается в журнал сервиса.

**Итог выполнения плана тоже пишет код.** Если что-то из плана или запроса не сделано, заголовок итога не говорит «успешно» («Выполнение завершено, но не все шаги выполнены.» или «Шаги плана выполнены, но не всё из запроса сделано — см. ⚠️ ниже.»), а несделанное перечисляется в блоке «Не выполнено». Списки изменений этапа выводятся полностью, без сокращения «и ещё N». Кроме того, код проверяет развёрнутые процесс, тип и записи и добавляет в блок «Не выполнено» строку в каждом из таких случаев:

- задача без своей формы не запрашивает поля, обязательные для перехода на следующий этап;
- справочник создан пустым, и ни один развёрнутый процесс к нему не обращается;
- поле причины (например, комментарий к отказу) процесс не заполняет: комментарий задачи остаётся только в её истории;
- проверка, с каких этапов можно перейти на этап, не добавлена, потому что у задачи нет второго выхода и при отказе запись осталась бы в ней навсегда.

Одинаковые строки объединяются: одна строка называет набор полей или проверку этапа вместе со всеми задачами, к которым она относится.

     - | до 3 (свойство ``citeck.ai.agent-execution.max-retries-per-step``); 
       | поисковые и аналитические этапы — до 2 (``max-retries-search-analyze``); если и они не удались, этап пропускается автоматически, без вопроса пользователю.
   * - Время исполнения конвейера
     - | 10 минут по умолчанию (свойство ``citeck.ai.agent-execution.max-wall-time``); считается только время исполнения — ожидание ответа человека не учитывается, после «Повторить» отсчёт начинается заново. 
       | По исчерпании прогон **ставится на паузу**, а не обрывается: сделанное сохраняется, пользователю предлагаются «Повторить», «Пропустить» и «Отменить»; этапы публикации после истечения срока доводятся до конца.
   * - Общий срок жизни запроса
     - | 30 минут по умолчанию (свойство ``citeck.ai.agent-execution.request-timeout``); 
       | должен быть строго больше ``max-wall-time``, иначе приложение не запускается.
   * - Параллельное исполнение этапов
     - | до 4 независимых этапов одной волны одновременно (свойство ``citeck.ai.agent-execution.parallel-steps``; 
       | значение ``1`` возвращает последовательное исполнение). Публикация и этапы, требующие подтверждения, параллельно не выполняются.
   * - Вызовов инструментов на один запрос в цикле агента
     - | до 60; 
       | при повторных сбоях одного инструмента (3 сбоя подряд или 2 сбоя с одинаковой ошибкой) инструмент блокируется до конца запроса. 
       | Один инструмент можно вызвать не более 20 раз за запрос и не более 3 раз подряд с одинаковыми аргументами. 
       | Эти ограничения действуют в диалоге с агентом. При автономном (stateless) вызове агента — из BPMN-процесса и через ``POST /api/ai-agent/execute`` (см. :ref:`режимы выполнения <agent-execution-modes>`) — счётных ограничений нет: отклоняется только точный повтор вызова с теми же аргументами (более 3 раз подряд либо после двух одинаковых отказов). Отклонённый вызов не выполняется, и модель должна ответить по уже собранным данным.
   * - Вызовов инструментов при генерации документации приложения
     - до 40; после этого инструменты перестают выполняться и модель завершает документ по собранному, на 50-м вызове генерация прерывается
   * - Генераций изображений на один диалог
     - до 20
   * - Повторы обращения к LLM-провайдеру при сетевых сбоях
     - 3 попытки с нарастающей задержкой
   * - Перегрузка провайдера (HTTP 429)
     - | пользователь видит сообщение «Провайдер модели <имя> перегружен (HTTP 429), повторите через N секунд.»; время ожидания берётся из заголовка ``Retry-After`` ответа провайдера, а если провайдер его не передал — сообщение заканчивается словами «повторите позже»;
       | исчерпание квоты — отдельное сообщение «Провайдер модели <имя>: исчерпан лимит запросов (HTTP 429), обратитесь к администратору.»;
       | сервис ассистента отвечает на такой запрос кодом HTTP 502; при перегрузке во время исполнения плана конвейер ставится на паузу с кнопкой «Повторить»

Ограничения защищают от неконтролируемого расхода токенов и зацикливания; при достижении лимита агент останавливается с уже собранным результатом и явно сообщает об этом, а конвейер при исчерпании времени ставится на паузу.
