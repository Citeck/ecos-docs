Описание микросервиса Process и предпосылки
============================================================================

Микросервис **ecos-process** управляет развёртыванием и исполнением BPMN-процессов на базе **Camunda 7**. Описание ниже соответствует исходникам ecos-process **2.38.0-SNAPSHOT**, использующим Camunda **7.24.0**.

Хранение данных
----------------

В микросервисе используются несколько уровней хранения:

.. list-table::
   :widths: 15 35
   :header-rows: 1
   :class: tight-table

   * - Данные
     - Хранение и назначение
   * - Состояние исполнения и история Camunda
     - Реляционная БД через JDBC-источник ``camunda``. В поставляемой конфигурации используется PostgreSQL.
   * - Определения и ревизии процессов ECOS
     - Собственные репозитории ecos-process, включая адаптеры ecos-data. Для определений используются таблицы ``process_def`` и ``process_def_rev``.
   * - Инстансы и версии состояний ECOS
     - Отдельные репозитории модели ECOS. Для них также предусмотрены адаптеры ecos-data и legacy MongoDB.
   * - Артефакты BPMN
     - Доставляются через ecos-apps, принимаются обработчиком артефактов BPMN и развёртываются в движке. Ревизии определения в ecos-process и deployment Camunda имеют собственное хранение.

В конфигурации приложения определены PostgreSQL-источники ``camunda`` и ``eproc``. Схема Camunda управляется Liquibase; автоматическое обновление схемы самим движком отключено.

MongoDB и миграция репозиториев
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Для собственных репозиториев ECOS сохранена поддержка MongoDB в legacy-режиме. Код содержит миграцию ``mongo-to-ecos-data-migration2``; выбор основного репозитория зависит от настроек и состояния миграции на конкретном стенде.

В поставляемом ``application.yml`` заданы ``ecos-process.mongo.enabled: true`` и ``ecos-process.repo.mongo.enabled: false``. Эти параметры управляют разными аспектами: доступностью MongoDB и использованием Mongo-репозиториев как основных. Они не определяют хранилище runtime Camunda.

Отключение MongoDB необходимо согласовать с завершением миграции существующих данных. При старте выполняется проверка допустимости такого отключения; перед изменением настроек проверьте состояние миграции на своём стенде.

Модель версионируемых состояний ECOS
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

В собственной модели ECOS операция ``ProcServiceImpl.updateStateData`` создаёт новую версию ``ProcessStateEntity`` и обновляет ссылку инстанса на неё. Этот механизм относится к репозиториям ECOS. Исполнение BPMN и сохранение его runtime-состояния выполняет Camunda через JDBC и свой менеджер транзакций.

Наличие предыдущих версий состояния не даёт универсального отката всех действий процесса. Внешние эффекты, например отправленные уведомления или изменения документов, требуют отдельного учёта и при необходимости компенсации.

Интеграции и масштабирование
-----------------------------

* **ecos-apps** доставляет и версионирует артефакты; ecos-process хранит определения и развёртывает их в Camunda.
* **EventsService** связывает события платформы с подписками BPMN. Для обмена сообщениями используется RabbitMQ; :ref:`интеграция событий <bpmn_events_integrations>` описана отдельно.
* **Hazelcast** используется для распределённых кешей, например поиска активного определения по типу и преобразования данных задач. Транзакции runtime Camunda обеспечиваются интеграцией движка с JDBC и транзакционной инфраструктурой платформы.

Отказоустойчивость, сохранность данных и горизонтальное масштабирование зависят от конфигурации экземпляров сервиса, БД, брокера, репликации и резервного копирования. Маршрутизация вызовов должна учитывать транзакционный контекст платформы. Увеличение числа экземпляров сервиса само по себе не гарантирует сохранность данных при любом отказе или неизменную производительность при росте истории процессов.

Транзакции и обработка событий
-------------------------------

Для JDBC-источника ``camunda`` выбирается менеджер транзакций: ``EcosTxnToSpringTxnManagerAdapter`` для управляемого источника или ``DataSourceTransactionManager`` для обычного источника. В поставляемой конфигурации источники ``camunda`` и ``eproc`` помечены ``xa: true``.

При обработке события Citeck сервис находит подходящие подписки BPMN, вычисляет атрибуты модели и проверяет предикат каждой подписки. Для совпавших подписок выполняется команда отправки сигнала в Camunda; затем движок продолжает исполнение процесса.

Изменения runtime-состояния сохраняются в транзакциях движка. Границы согласованности внешних команд, событий и действий зависят от конкретной операции и её участия в транзакционном механизме. Их нельзя описывать как единый цикл с обязательным созданием новой версии ``ProcessStateEntity`` при каждом переходе BPMN.
